## 自动测试命令

在比赛模块根目录运行：

```powershell
npm test
```

若需要检查单个测试文件，使用实际存在的文件名：

```powershell
node --test test/*.test.mjs
```

验收要求：退出码为 `0`，无跳过的安全关键测试，无未处理 Promise rejection。任何失败都应保留原始摘要并在修复后重新执行全量测试。

## 模型误差与研究有效性计划

当前 30 项自动测试验证的是软件契约、安全边界和完整性，不是交易模型的现实有效性。以下项目在获得有时间顺序、授权且不泄漏未来信息的评估数据之前保持 `TBD`，不得预填通过：

| ID | 范围 | 操作 | 验收证据 |
| --- | --- | --- | --- |
| V-01 | 错误分类 | 在独立、带现实标签的时间序列样本上计算混淆矩阵 | 样本定义、时间窗口、标签方法、各类 precision/recall；当前 TBD |
| V-02 | 概率校准 | 计算 Brier score 或等价校准指标，并绘制可靠性分箱 | 指标、分箱、置信区间与基线；当前 TBD |
| V-03 | 漂移 | 比较训练/设定期与评估期特征、类别概率分布 | 漂移指标、阈值和处置记录；当前 TBD |
| V-04 | 缺失特征敏感性 | 逐项移除公开特征并复算候选动作 | 缺失披露、概率变化和风险处置；计划执行，当前 TBD |
| V-05 | 上游错误敏感性 | 注入错误、极端、延迟或相互矛盾的来源值 | 校验拒绝或结果变化可见；计划执行，当前 TBD |
| V-06 | 收益性边界 | 检查所有报告和答辩是否把软件测试误作收益证据 | 不出现未经支持的准确率、收益、胜率或超额收益陈述 |

当前模型不是生成式 LLM，因此没有自由文本幻觉测试路径；测试重点是结构化误判、错误输入、零填充、概率未校准和使用者误读。若未来增加 LLM 摘要，必须单独测试引用一致性、无依据陈述、提示注入和输出对核心决策的隔离。

## 连续场景验收

### 建设性场景

运行 `offline-constructive`。验收重点不是候选方向本身，而是：模型确实给出概率与贡献、风险逐条执行、最终动作与订单状态一致、完整性验证通过。

### 证据过期场景

运行 `stale-evidence`。预期 `EVIDENCE_FRESHNESS` 失败；若模型给出可执行候选动作，风控必须将最终动作回落为 `HOLD` 且不创建订单。

### 风险超限场景

运行 `risk-limit`。预期至少一个金额或仓位规则失败，产物保留候选动作和失败原因，但不创建订单。

### 真实公开数据场景

联网运行 `public-btc-live`：

- CoinLore、Coin Metrics Community、Alternative.me、GitHub 均使用实际公开 HTTPS 接口且无需 API Key；
- 记录四源成功数、参考价格、候选动作、最终动作和验签结果；
- 对比每个来源的 `retrievedAt` 与 `asOf`，确认市场快照、日线指标与开发活动没有被表述为同频；
- 确认四个模型特征和一个 `RISK_REFERENCE` 价格证据均可由 `raw` 与白名单 `transform_id` 重算；
- 确认逐指标新鲜度、至少 50% 特征覆盖、collection 来源健康和参考价绑定规则可见；
- 确认真实公开输入仍只产生 Paper 模拟或不创建订单；
- 断开一个非市场源时，确认状态明确且不出现合成特征；
- CoinLore 市场源不可用时，确认失败关闭而不是回退 fixture；
- 检查运行前后工作区，确认没有保存第三方原始 JSON。

### 可选本地研究场景

分别在本地 `8790` 可用和不可用时测试：

- 可用：只读取、严格校验和标明来源；
- 不可用：返回明确错误或不可用状态，不伪造成功、不影响离线场景；
- 两种状态都不得访问订单、账户或凭据接口。

## UI 与可访问性检查

在至少以下视口检查：

- Desktop：`1440 × 900`；
- Mobile：`390 × 844`。

检查项：

- 页面非空，核心状态无需横向滚动即可理解；
- 控件文字不溢出，面板不重叠；
- 键盘可选择场景、运行、验证、下载和查看 JSON；
- 加载、成功、否决、验证失败和 API 错误均有可见状态；
- 公开场景能区分来源状态、抓取时间和来源时间；
- 不只依赖颜色表达通过/失败；
- `decision_id`、哈希、公钥和签名长文本可换行或截断且能复制；
- 页面始终显示 Paper-only 和免责声明；
- 不显示收益、PnL 或真实余额暗示。

建议保存桌面与移动截图作为提交证据，但截图只能记录实际运行结果。

## 源码与便携包测试

当前源码 checkout 的可复现入口为：

```powershell
cd app
npm ci
npm run check
npm test
```

源码仓库不包含此前便携 handoff 使用的 `build-submission.ps1` 或 `build-portable-windows.ps1`。如果团队重新生成便携包，必须由独立白名单流程完成构建，并按下列清单重新验收。

验收：

1. 构建成功且打印 ZIP 路径、文件数量和 ZIP SHA-256；
2. ZIP 内存在 `manifest.sha256`；
3. 不存在 `.env`、`node_modules`、`output`、`dist`、日志、缓存、账户数据、私钥、token 或第三方原始 API 响应；
4. 将 ZIP 解压到新的空目录；
5. 在解压目录运行 `npm test` 和 `npm start`；
6. 对清单中每个文件重新计算 SHA-256 并与 manifest 对比；
7. 最终 ZIP 不引用工作区外的绝对路径作为运行依赖。

## 回归门槛

以下任一条件不满足，不应提交：

- 自动测试退出码非零；
- 实盘模式未被阻断；
- 风控否决后仍生成订单；
- 任一篡改样本仍验证通过；
- 公开接口失败后出现合成回退，或 CoinLore 市场源失败后仍生成决策；
- 外部请求、报告或提交包含客户、账户、组合、钱包、凭据或主动收集的个人数据；
- 将 Paper-only 错误描述为模拟行情，而不是模拟执行；
- 把当前自动 Paper 结果描述成已经具备实盘人工审批；
- 把非生成式模型描述成“不会幻觉/不会错误”，或把软件测试写成预测准确率/盈利性证据；
- 离线场景依赖 `.env`、网络或旧 Agent；
- ZIP 含敏感文件或秘密扫描命中；
- UI 无法清楚显示来源、模型、风控和验证状态；
- 文档、视频与实际 API/行为不一致。
- 官方评分字段、技术门槛、视频时长、跨境复核或 `>=70%` 新增证据仍为 TBD，却在提交材料中写成已完成。

- 执行者或复核者。
